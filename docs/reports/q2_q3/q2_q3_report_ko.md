# PIIGuard 질문 2·3: 노이즈는 얼마나 손해이고, 노이즈로 학습하면 되찾을 수 있는가?

*분석 보고서. PIIGuard 팀 (Louis Lenoble, Sunho Cha, Suseong Kim), CSED490E, 2026년 11월 24일.*

## 요약

질문 2는 질문 1의 세 탐지기(규칙만 쓰는 Presidio, Gravitee의 BERT, GLiNER)를 같은 테스트셋의 노이즈 사본에 그대로 실행한다. 질문 3은 그 BERT를 clean ai4privacy 텍스트로, 또는 같은 텍스트에 레코드마다 노이즈 사본 하나를 더해 파인튜닝하고 두 버전을 비교한다. 채점, 매칭, 통계는 질문 1([보고서](../q1/q1_report_ko.md))과 같다. 엄격 일치(strict matching) 기준의 micro F2와 유출률을 쓰고, 95% 구간은 대응 클러스터 부트스트랩으로, 검정은 대응 랜덤화 검정과 Holm 보정으로 했다.

1. **띄어쓰기 오류가 가장 크고, 그다음이 오타다.** 6개 라벨 기준으로 열 단어에 한 번꼴로 띄어쓰기를 빼거나 넣으면 BERT는 F2가 0.069~0.116, GLiNER는 0.014~0.076 떨어진다.
2. **GLiNER가 BERT보다 오타, 띄어쓰기, 혼합 노이즈에 강하다.** 세 데이터셋 모두 그렇다. 혼합 사본에서 BERT가 0.018~0.026 더 떨어지고, 95% 구간이 모두 0 아래다. 예외는 소문자다. BERT는 전혀 영향을 받지 않지만(토크나이저가 소문자로 바꿈), GLiNER는 ai4privacy에서 F2 0.028을 잃고 유출률이 3.0%p 오른다.
3. **숫자 형식 노이즈는 날짜를 깨뜨린다.** 모든 날짜를 채점하면(비교 A-dates) 구분자를 지우거나 섞었을 때 Nemotron-PII에서 Presidio는 F2 0.241, BERT는 0.066을 잃는다.
4. **자기 도메인에서는 노이즈 사본 학습이 하락의 2/3를 되찾는다.** ai4privacy에서 clean으로만 학습한 BERT는 혼합 사본에서 F2 0.071을 잃는다. clean+noisy로 학습한 버전은 거기서 0.047 [0.044, 0.050] 더 높고, clean 텍스트에서의 손해는 0.003이다(검출은 되지만 기준인 0.01 미만).
5. **다른 데이터셋에서는 noisy 버전이 clean을 포함한 모든 테스트셋에서 낫다.** clean Nemotron-PII에서 +0.068, clean Gretel에서 +0.026, 혼합 사본에서 +0.126과 +0.060이고, 유출률도 낮다. 이 차이는 모두 확인되었고, noisy 버전의 모든 seed가 clean 버전의 모든 seed보다 높다.
6. **ai4privacy만으로 파인튜닝해서는 다른 데이터에 더 좋은 탐지기가 되지 않는다.** 두 파인튜닝 버전 모두 Gretel에서 원본 BERT보다 낮다(0.51~0.53 대 0.72). 주로 주소 때문인데, ai4privacy는 건물번호와 도로명까지만 주소로 표시한다. proposal 부록 B대로 파인튜닝 버전은 서로끼리만 비교한다.

세 질문의 핵심 표는 3쪽 PDF [results_tables.pdf](../results_tables/results_tables.pdf)(영어)에도 있다.

## 1. 질문

> **Q2.** 빠르게 타이핑할 때 생기는 실수가 텍스트에 있으면 Presidio, BERT, GLiNER는 얼마나 손해를 보는가(proposal 4.2절)?
>
> **Q3.** 노이즈 텍스트로 BERT를 파인튜닝하면 그 손해를 되찾는가, 그리고 clean 텍스트에서는 무엇을 잃는가(proposal 5.2절, 부록 B)?

두 질문 모두 질문 1의 테스트셋, 라벨, span 정리, 탐지기, 채점, 비교를 그대로 쓴다. 바뀌는 것은 텍스트(질문 2) 또는 BERT 가중치(질문 3)뿐이다.

## 2. 노이즈 테스트셋

### 2.1 노이즈 종류

`benchmark/noise.py`는 proposal 4.2절의 실수 종류마다, 그리고 그것들을 섞은 것까지 텍스트의 노이즈 사본을 하나씩 만든다.

| 종류 | 편집 | 예 (가상) |
| --- | --- | --- |
| `typo` (오타) | 3글자 이상 단어에서 글자 추가, 삭제, 다음 글자와 교환, 또는 QWERTY 옆 키로 바꾸기 | example → exmaple |
| `space` (띄어쓰기) | 단어 사이 공백 삭제, 또는 4글자 이상 단어 안에 공백 추가 | is minji.park@... → isminji.park@... |
| `case` (소문자) | 대문자가 있는 단어를 소문자로 | Minji Park → minji park |
| `punct` (구두점) | 문장·절 끝 구두점 삭제(`x@y.com`이나 `1,234` 안은 제외) | 문장이 이어 붙음 |
| `number` (숫자 형식) | 숫자의 구분자를 지우거나 섞기(공백, 하이픈, 없음) | 010-2345-6789 → 01023456789 |
| `mixed` (혼합) | 편집마다 위 다섯 종류 중 하나를 무작위로 | |

### 2.2 정답 span이 텍스트를 따라가는 방식

모든 편집은 원문의 비어 있지 않은 범위를 바꾸고, 편집끼리는 겹치지 않는다. 편집은 정답 span 안에 있거나 모든 span 밖에 있다. span 경계를 가로지르는 편집은 하지 않는다. 그러면 span은 텍스트를 따라 움직이고(시작은 앞쪽 편집의 길이 변화만큼, 끝은 span 안쪽 편집의 길이 변화까지 더해), 라벨을 유지하며(오타 난 이메일도 이메일이다), 다른 정답 span과 같은 규칙으로 정리된다.

첫 버전을 점검하다가 규칙 하나를 더했다. 같은 라벨의 두 값 사이에 공백만 남기는 편집은 하지 않는다. "Roger Leblanc, Roger Leblanc"에서 쉼표를 지우면 span 정리가 두 이름을 하나의 정답으로 합쳐서, 노이즈가 정답 자체를 바꾸기 때문이다. 이 규칙 덕분에 **모든 노이즈 테스트셋은 라벨별 정답 span 수가 clean 버전과 정확히 같다**(36개 모두 확인).

### 2.3 강도와 seed

사본마다 round(0.10 × 단어 수)번, 최소 한 번 편집한다. 대략 열 단어에 한 번이다. 해당 종류의 노이즈를 넣을 자리가 적은 텍스트는 편집이 적다(숫자가 없는 텍스트의 `number` 사본은 그대로다). 강도와 seed(1)는 채점 전에 정했다. 예시마다 `Random("<seed>:<kind>:<예시 id>")`로 따로 난수를 뽑으므로, 사본이 예시 순서에 좌우되지 않는다. A-dates 버전은 6개 라벨 버전과 같은 편집을 받는다. 두 정답 span 목록을 함께 넘기고, 어느 쪽 경계도 넘지 않게 하기 때문이다.

노이즈 테스트셋은 `data/test/<dataset>_noisy_<kind>[_dates].jsonl`(데이터셋 3 × 종류 6 × 라벨 집합 2 = 36개)이고, id는 clean과 같다. 각 예시의 `meta.noise`에 편집 목록과 각 편집이 값 안에 있는지가 적혀 있다.

### 2.4 노이즈 테스트셋의 모습

`results/noise/test_sets.md` 기준:

| 데이터셋 | 예시 | 예시당 편집 (혼합) | PII 값 안의 편집 (혼합) | `number`로 바뀐 예시 |
| ------------ | -----: | ----------: | ---------------: | --------------: |
| ai4privacy | 10,000 | 1.7 | 18.1% | 2,487 |
| Nemotron-PII | 2,000 | 13.2 | 5.2% | 1,711 |
| Gretel | 2,962 | 19.1 | 5.8% | 1,992 |

ai4privacy 문장은 짧고 PII가 빽빽해서 편집 다섯 개 중 하나꼴로 값을 건드린다. 긴 Nemotron-PII와 Gretel 문서에서는 대부분의 편집이 값 주변 단어에 들어간다. 값 안쪽은 `case`(ai4privacy 38%)와 `number`(59%)가 가장 많이 건드리고, `punct`는 거의 건드리지 않는다(값이 문장 끝 기호로 끝나는 일이 드묾).

## 3. BERT 파인튜닝

### 3.1 데이터

`experiments/prepare_train.py`는 ai4privacy **train** split의 영어 레코드(120,533개, 우리 ai4privacy 테스트셋은 validation split에서 뽑았다)를 읽고, 5,000개를 dev로 떼어 두고(seed 0), 나머지 115,533개를 학습에 쓴다. 모든 레코드의 혼합 노이즈 사본도 하나씩 만드는데, 노이즈 테스트셋과 같은 방식이지만 **seed 2**를 써서 테스트 사본을 학습에서 보는 일이 없다.

| 파일 | 레코드 | NAME | EMAIL | PHONE | ADDRESS | DATE | CARD_NUMBER |
| ---------------- | ------: | ----------------------------------------: | -----: | -----: | ------: | -----: | ----------: |
| train clean | 115,533 | 101,783 | 13,282 | 17,984 | 17,487 | 16,391 | 2,148 |
| train noisy | 115,533 | span 동일, 편집 201,528개(레코드당 1.7개, 21%가 값 안) |  |  |  |  |  |
| dev clean, noisy | 각 5,000 | 4,443 | 592 | 760 | 765 | 692 | 104 |

버전 **(a)**는 train clean으로, 버전 **(b)**는 train clean + train noisy로 학습한다.

### 3.2 라벨과 태그

두 버전 모두 벤치마크의 BERT(`gravitee-io/bert-small-pii-detection`, revision `f8c27a85c5`)에서 시작해 51개 BIO 태그를 그대로 유지한다. 그래서 `baselines/bert_detector.py`가 원본 모델과 똑같이 읽는다. 우리 라벨은 모델의 기존 클래스로 가르친다.

| 우리 라벨 | BERT 클래스 |
| ------------ | ------------- |
| NAME | PERSON |
| EMAIL | EMAIL_ADDRESS |
| PHONE | PHONE_NUMBER |
| ADDRESS | LOCATION |
| DATE (모든 날짜) | DATE_TIME |
| CARD_NUMBER | CREDIT_CARD |

모든 날짜는 비교 C처럼 DATE_TIME으로 가르친다. ai4privacy에는 생년월일 라벨이 없어서, 날짜를 태그하지 않으면 모델이 날짜 클래스를 잊게 된다. 6개 라벨 비교에서는 원본 모델과 마찬가지로 탐지기가 DATE_TIME을 DATE_OF_BIRTH로 읽는다. 나머지 토큰은 모두 `O`라서, 도시나 직함 같은 것은 우리 라벨이 아니라는 것도 배운다. 토큰은 첫 글자가 속한 span을 따른다. span의 첫 토큰은 `B-`, 다음 토큰은 `I-`, `[CLS]`와 `[SEP]`는 무시(-100)한다.

### 3.3 학습 레시피

| 설정 | 값 |
| --- | --- |
| Trainer | Hugging Face `Trainer`, AdamW(기본값), linear schedule |
| 학습률 | 5e-5, 처음 6% step 동안 warm-up |
| Weight decay | 0.01 |
| Batch | 32 |
| Step | **두 버전 모두** 10,832: clean 학습셋 3회분. 버전 (b)는 각 레코드를 1.5번 본다 |
| 길이 | 256토큰, `BertDetector`가 읽는 창 크기(레코드 중앙값 29토큰, 115,533개 중 1개만 잘림) |
| 정밀도 | bf16 |
| 체크포인트 | 마지막 step. dev는 기록만 하고 모델 선택에 쓰지 않음(noisy dev는 버전 b에 유리하므로) |
| Seed | 버전마다 0, 1, 2 (모델 6개) |

(a)와 (b)의 차이는 노이즈 사본뿐이다. 시작 모델, 설정, step 수, seed 목록이 같다. 하이퍼파라미터 탐색은 하지 않았다. 설정은 `experiments/train_bert.py`에 고정되어 있고, 실행마다 기록(설정, 데이터 체크섬, 모든 loss, 시간, GPU, 패키지 버전)을 `results/training/<model>.json`에 남긴다.

### 3.4 학습 실행

모델마다 GPU 한 장에서 약 2분 걸렸다(RTX 4090 다섯 번, L40S 한 번). torch 2.14.1, transformers 5.16.1이다(`results/training/summary.md`). 학습 중 dev loss, seed 3개 평균:

| 모델 | Dev 셋 | step 1,805 | 3,610 | 5,415 | 7,220 | 9,025 | 10,830 |
| ----------------- | ----- | ---------: | -----: | -----: | -----: | -----: | -----: |
| (a) clean | clean | 0.0173 | 0.0135 | 0.0127 | 0.0128 | 0.0127 | 0.0122 |
| (a) clean | noisy | 0.0945 | 0.1048 | 0.1143 | 0.1250 | 0.1352 | 0.1335 |
| (b) clean + noisy | clean | 0.0210 | 0.0162 | 0.0146 | 0.0129 | 0.0134 | 0.0130 |
| (b) clean + noisy | noisy | 0.0411 | 0.0319 | 0.0285 | 0.0264 | 0.0269 | 0.0258 |

clean으로만 학습한 버전은 학습이 진행될수록 noisy dev에서 *나빠진다*(0.095 → 0.134). 세 seed 모두 그렇다. 학습 데이터의 깨끗한 표기에 점점 더 맞춰지는 것으로 보인다. 버전 (b)는 두 dev 모두 좋아진다.

## 4. 평가와 통계

- **실행.** Presidio, BERT, GLiNER를 질문 1 설정(GLiNER 컷오프 0.35, revision 고정)으로 노이즈 테스트셋 36개에 실행했다. Presidio는 CPU로 3분, BERT는 GPU 1장으로 16분, GLiNER는 3장으로 48분 걸렸다. 파인튜닝 모델 6개는 clean과 노이즈 테스트셋(모델당 42개)에서 같은 `BertDetector`로 실행했다. 예측은 모두 `results/predictions/`에 있다.
- **점수.** 바꾸지 않은 `experiments/score.py`로 micro P, R, F1, F2, 유출률을 엄격 일치, 비교 A, B, A-dates, B-dates로 계산했다. 파인튜닝 버전의 점수는 seed 3개의 평균이다.
- **구간과 검정**(`experiments/significance_noise.py`). 질문 1의 방법을 그대로 썼다. 95% 구간은 대응 클러스터 부트스트랩(10,000회)으로, 검정은 대응 근사 랜덤화 검정으로 했다. 클러스터는 clean 테스트셋 기준이라 노이즈 사본이 항상 원래 예시와 함께 뽑힌다. 파인튜닝 버전은 부트스트랩과 랜덤화의 매 회차에서도 seed 평균을 쓰고, 검정은 두 버전의 출력을 seed 쌍 세 개에 대해 한꺼번에 바꾼다. 검정 묶음은 셋이고, 각각 F1, F2, 유출률에 Holm 보정을 했다. 세 탐지기의 노이즈 사본별 변화(216개), 모든 테스트셋에서 noisy 버전과 clean 버전의 차이(84개), 파인튜닝 버전의 노이즈 사본별 변화(144개)다. 묶음이 질문 1보다 커서 랜덤화는 20,000회로 했다.
- **확인**의 기준은 질문 1과 같다. 보정 p가 0.05 미만이고, 구간이 0을 포함하지 않으며, 차이가 0.01 이상이어야 한다.

아래 표에서 *기울임꼴* 값은 확인되지 않은 값이고, 질문 3 표의 **굵은 차이**는 확인된 값이다. 모든 구간은 `results/analysis/significance_noise.md`에 있다.

### 해석

1. **띄어쓰기, 그다음 오타.** 단어가 붙거나 쪼개지면 모델이 보는 토큰이 달라져서 예측 span의 경계가 움직이고, 엄격 일치에서는 놓친 것으로 센다. 다섯 종류 중 띄어쓰기 사본이 비교 A의 모든 데이터셋에서 BERT와 GLiNER의 가장 큰 하락이다. A-dates에서는 숫자 노이즈가 비슷한 수준이고, Nemotron-PII의 GLiNER에서는 띄어쓰기보다 크다.
2. **소문자는 모델뿐 아니라 파이프라인 검증이기도 하다.** BERT의 토크나이저는 대소문자를 구별하지 않아서, 소문자 사본에서의 출력이 clean과 똑같다. 그래야 맞다. GLiNER는 대문자를 이름의 단서로 쓰기 때문에 소문자 이름을 더 자주 놓친다.
3. **Presidio의 약점은 형식이다.** 규칙은 단어 노이즈에는 거의 영향이 없지만 숫자에는 크게 흔들리고, 날짜를 채점하면(A-dates) 가장 크게 떨어진다.
4. **값 주변 단어의 노이즈도 중요하다.** Nemotron-PII와 Gretel에서 띄어쓰기 편집 중 값 안에 들어간 것은 2~4%뿐인데도, BERT는 그 사본에서 F2를 약 0.07 잃는다.

### 6.1 왜 두 파인튜닝 버전이 다른 도메인에서 원본 BERT보다 낮은가

clean 테스트셋의 라벨별 F2, 비교 A (파인튜닝은 seed 3개 평균):

| 데이터셋 | 라벨 | gold 값 | 원본 BERT | (a) clean | (b) clean + noisy |
| ------------ | ----------- | -----: | ------: | --------: | ----------------: |
| Gretel | ADDRESS | 2,322 | 0.80 | 0.13 | 0.13 |
| Gretel | NAME | 4,475 | 0.85 | 0.73 | 0.77 |
| Gretel | EMAIL | 837 | 0.85 | 0.70 | 0.81 |
| Gretel | CARD_NUMBER | 76 | 0.71 | 0.36 | 0.43 |
| Nemotron-PII | EMAIL | 1,091 | 0.95 | 0.63 | 0.82 |
| Nemotron-PII | CARD_NUMBER | 257 | 0.95 | 0.42 | 0.65 |
| Nemotron-PII | ADDRESS | 324 | 0.45 | 0.60 | 0.65 |

- **주소.** ai4privacy는 건물번호와 도로명만 주소로 표시하고, Gretel은 주소 전체를 표시한다. ai4privacy로 학습한 두 버전은 짧은 경계를 배우고, Gretel에서 엄격 일치가 실패한다(0.80 → 0.13). 노이즈의 효과가 아니라 데이터셋 간 표기 관례의 차이이고, 노이즈 사본은 이를 바꾸지 못한다.
- **학습 데이터.** 원본 BERT는 Gretel의 PII finance 문서가 들어간 데이터로 학습했다(질문 1의 오염 분석 S3). ai4privacy만으로 다시 학습하면 그 이점을 잃는다.
- **이메일과 카드번호**는 다른 도메인에서 두 버전 모두 떨어지는데, 노이즈 사본이 하락을 절반쯤 줄인다(Nemotron-PII 이메일 0.63 → 0.82).
- 이름과 주소를 빼면(비교 B) Gretel에서 두 파인튜닝 버전이 원본 BERT보다 *높다*(0.507, 0.524 대 0.459). 위 분석과 일치한다.

그래서 proposal은 두 파인튜닝 버전을 서로끼리만 비교한다. 둘은 노이즈 사본 말고는 모든 것이 같고, 원본 BERT는 다른 데이터로 학습했기 때문이다.

## 7. 결론

1. 노이즈는 모든 탐지기에 손해이고, 띄어쓰기 실수가 가장 크다. LLM 앞의 필터로 보면 두 신경망 탐지기 중 BERT가 더 취약하고, GLiNER는 소문자 이름을 빼면 더 강하다.
2. 노이즈 사본 학습은 자기 도메인에서 효과가 있다. 하락의 약 2/3를 되찾고, clean 텍스트에서는 의미 있는 손해가 없다.
3. 다른 도메인에서는 노이즈 사본이 정규화 역할도 하는 것으로 보인다. clean으로만 학습한 버전은 ai4privacy의 깨끗한 표기에 과적합되는 것으로 보이고(학습 중 noisy dev loss가 오름), noisy 버전은 clean 텍스트에서도 더 좋다.
4. 자기만의 span 관례가 있는 데이터셋 하나로 파인튜닝해서는 다른 데이터에서 원본 BERT를 이기지 못한다. 더 좋은 탐지기를 만들려면 라벨 경계가 대상 텍스트와 맞는 학습 데이터가 필요하다.

## 8. 한계

- **합성 노이즈.** 편집은 스크립트로 만들었고 강도는 0.10 하나다. 실제 타이핑 실수의 분포는 다르며, 다른 강도는 시험하지 않았다.
- **학습 도메인 하나.** 두 버전 모두 ai4privacy로만 학습해서, 다른 도메인 결과에는 노이즈 효과와 span 관례 효과가 섞여 있다(6.1절).
- **Seed.** 검정은 학습 seed 3개를 고정된 것으로 보고 테스트 예시의 변동만 다룬다. 다른 학습 실행에 대해서는 말하지 않는다. seed 수준 점검(확인된 차이에서 (b)의 모든 seed가 (a)의 모든 seed보다 높음)이 그 일부를 보완한다.
- **중복.** ai4privacy 테스트 문장 10,000개 중 89개(0.9%)가 ai4privacy train split에도 글자 그대로 있다. 두 버전 모두 봤으므로 버전 간 비교는 공정하지만, 두 버전의 도메인 내 점수는 약간 낙관적이다.
- **튜닝 없음.** 학습 설정은 실행 전에 정한 한 가지이고 두 버전에 같다. 어느 쪽이든 더 좋은 설정이 있을 수 있다.
- **엄격 일치만.** 질문 1처럼 경계 하나가 틀리면 놓친 것으로 센다. 질문 1 민감도 분석의 느슨한 매칭은 노이즈 사본에서 다시 돌리지 않았다.
